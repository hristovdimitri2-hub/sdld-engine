# ARCHITECTURE.md: Автономен инженерен двигател

Версия 1.0. Документът описва цялата архитектура: компоненти, данни, състояния, договори, грешки, сигурност и фази на изграждане.

---

## 1. Цел и принципи

**Цел:** на входа се подава цел ("направи X"), а на изхода излиза проверен, работещ продукт. Човекът не е "кабел" между моделите. Той се намесява само при решения с висок риск.

**Седем принципа (всеки решава конкретен проблем):**

| # | Принцип | Проблемът, който решава |
|---|---|---|
| 1 | Оркестраторът е **код**, не модел | Грешките на модела не се натрупват в управлението |
| 2 | **Съдията е детерминиран** (тестове, компилатор, симулация) | Консенсус на модели не е доказателство |
| 3 | Всяко твърдение е **проверимо** (изпълнение или източник) | Халюцинации |
| 4 | Всяка задача е **малък договор** с критерии | Дрейф и размиване на целта |
| 5 | **Едно състояние**, записано трайно (SQLite) | Срив на процес = загубена работа |
| 6 | **Минимални права** за всеки агент и инструмент | Ограничава щетите при грешка или атака |
| 7 | **Бюджет и лимити** навсякъде | Безкрайни цикли и изненадващи сметки |

## 3. Компоненти

### 3.1 Оркестратор
Програма, която върти конечен автомат (раздел 5). На всеки "тик": взима следващата готова задача, проверява бюджет и политика, вика агент, записва резултата, преминава в ново състояние. **Не взима творчески решения.** Те се делегират на агенти, а оркестраторът само валидира резултата им по схема.

### 3.2 Scheduler
Определя кои задачи са готови: всички зависимости са `DONE` и няма конфликт по файлове. Паралелно вървят само задачи с **непресичащи се множества от файлове** (`scope`). Всяка работи в собствен git worktree.

### 3.3 Agent Runner (адаптери)
Единен интерфейс `run(role, input) -> output`. Реализации:
- `ClaudeCodeAdapter`: вика `claude -p "<задача>" --output-format json` в worktree-то на задачата (това ползва твоя VS Code / Mimo настройка).
- `ApiAdapter`: вика евтин модел през API (Gemini Flash, DeepSeek и др.) през слой за абстракция (напр. LiteLLM).
- `LocalAdapter`: Ollama (по избор).

Смяната на модел е промяна в конфигурация, не в код.

### 3.4 Tool Gateway
Единственият път към външния свят. Всеки инструмент има: име, схема на вход, **списък на ролите, които могат да го ползват**, лимит на извиквания, одит лог. Агент не пуска `shell` или `http` директно.

### 3.5 Конектори
| Конектор | Режим по подразбиране | Забележка |
|---|---|---|
| GitHub | четене + бранч/PR; **без merge в main, без push в main** | токен с минимални права |
| Gmail | **само четене** | съдържанието е **недоверен вход** (раздел 9) |
| Файлове / репо | четене/писане само в worktree | |
| HTTP | allowlist от домейни | документации, API-та |

### 3.6 Съдия (Judge)
Набор от гейтове, зададени в `gates.yaml` за всеки проект: unit/integration тестове, lint, type check, secret scan, зависимости (audit), специфични проверки (бектест, тест-мрежа). Резултатът е `PASS` или `FAIL` с машинно четим отчет. **Нито един модел не може да отмени гейт.**

### 3.7 Журнал на грешките
Таблица `errors`: всяка грешка с клас, контекст, опити, решение (раздел 8). Чете се от Планиста преди всяка нова задача, а повторяемите грешки се превръщат в правила в `rules.md`.

### 3.8 Budget Guard
Дневен и по-задачен лимит за токени/пари/време/брой опити. При превишаване: пауза и известие.

### 3.9 Policy Engine
Решава дали едно действие е позволено автоматично, или иска одобрение (раздел 10).

### 3.10 Наблюдаемост
Всяко извикване на агент и инструмент се записва в `events` (вход, изход, цена, време). Малък уеб панел чете тази таблица на живо.

## 4. Модел на данните (SQLite)

```
goals(id, текст, статус, създадена)
specs(id, goal_id, съдържание, версия, одобрена_от, одобрена_на)
tasks(id, spec_id, договор_json, състояние, опити, бранч, worktree, зависи_от[], scope[])
runs(id, task_id, роля, модел, вход_ref, изход_ref, цена, време, статус)
critiques(id, task_id, run_id, твърдение, контрапример_ref, валидна)
errors(id, task_id, клас, съобщение, контекст_ref, решение, повтаряемост)
approvals(id, действие, риск, поискано_на, решение, решено_от)
budget_ledger(id, ден, task_id, токени, цена)
knowledge(id, източник_url, изтеглено_на, хеш, път)
memory_items(id, тип, съдържание, приоритет, обновено)
events(id, време, тип, данни_json)
```

Големи артефакти (diff-ове, логове) се пазят като файлове; в базата стои само референция (`*_ref`).

## 5. Конечен автомат на задачата

```
 PENDING ──(зависимостите са DONE)──► READY
 READY ──(scheduler я взима)──► BUILDING          (ТЕЗА)
 BUILDING ──(резултат валиден по схема)──► JUDGING
 JUDGING ──PASS──► REVIEWING
 JUDGING ──FAIL──► CRITIQUING                      (АНТИТЕЗА)
 CRITIQUING ──(валиден контрапример)──► RESOLVING  (СИНТЕЗ)
 CRITIQUING ──(няма контрапример, но FAIL от съдията)──► RESOLVING
 RESOLVING ──► JUDGING          (оборот++)
 REVIEWING ──(Критикът не намира контрапример)──► AWAITING_POLICY
 REVIEWING ──(намира валиден)──► RESOLVING
 AWAITING_POLICY ──(политика: авто)──► DONE
 AWAITING_POLICY ──(политика: човек)──► WAITING_HUMAN ──► DONE | REJECTED
 *  ──(оборот > макс | бюджет | неразрешим клас)──► ESCALATED
 ESCALATED ──(човек/нова спецификация)──► READY | CANCELLED
```

**Инварианти:**
- Преход става само чрез оркестратора, никога от агент.
- Всеки преход се записва в `events`.
- След срив процесът се възстановява от `tasks.състояние`; прекъснатите `BUILDING`/`JUDGING` се връщат в `READY` (операциите са идемпотентни).

## 6. Договори (JSON схеми, валидирани с Pydantic)

### 6.1 Task
```json
{
  "id": "T-014",
  "цел": "Валидиране на x402 плащане",
  "вход": ["docs/x402.md", "src/payments/"],
  "scope": ["src/payments/verify.py", "tests/test_verify.py"],
  "критерии": [
    {"id": "C1", "проверка": "pytest tests/test_verify.py::test_valid", "очаква": "pass"},
    {"id": "C2", "проверка": "pytest tests/test_verify.py::test_replay", "очаква": "pass"}
  ],
  "забрани": ["src/core/**"],
  "зависи_от": ["T-011"],
  "макс_оборота": 3,
  "риск": "среден"
}
```

### 6.2 AgentResult (Строител / Резолвер)
```json
{
  "task_id": "T-014",
  "резюме": "...",
  "променени_файлове": ["src/payments/verify.py"],
  "твърдения": [
    {"текст": "верифицира подписа по спецификацията", "доказателство": "C1"}
  ],
  "неизвестни": ["поведение при забавена верига"]
}
```
Полето `неизвестни` е задължително: агентът трябва да казва какво **не** знае вместо да го измисля.

### 6.3 Critique (Критик)
```json
{
  "task_id": "T-014",
  "възражения": [
    {
      "твърдение": "повторно плащане се отхвърля",
      "контрапример": {"тип": "тест", "път": "tests/crit/test_replay_race.py", "очаквано_падане": true},
      "тежест": "висока"
    }
  ]
}
```
**Правило за валидност:** възражение е валидно само ако оркестраторът изпълни контрапримера и той наистина падне върху текущия код. Възражение без изпълним контрапример се записва като `невалидно` и се игнорира.

### 6.4 ErrorRecord
```json
{"клас": "знание", "съобщение": "несъществуващ метод client.pay()", "контекст_ref": "runs/881/out.txt", "решение": "refetch_docs"}
```

## 7. Диалектичният цикъл (псевдокод)

```python
def process(task):
    while task.оборот <= task.макс_оборота:
        # ТЕЗА
        result = run("builder", task, context=memory + knowledge + rules)
        validate_schema(result)            # невалидно -> retry, брои се
        # СЪДИЯ
        verdict = judge.run(task.worktree, gates)
        if verdict.pass_:
            # АНТИТЕЗА (прегледът е по diff, не по целия проект)
            crit = run("critic", diff(task), spec=task.критерии)
            valid = [c for c in crit.възражения if executes_and_fails(c.контрапример)]
            if not valid:
                return policy.finalize(task)       # DONE или WAITING_HUMAN
            findings = valid
        else:
            findings = [verdict.report]
        # СИНТЕЗ
        run("resolver", task, findings)            # поправя точно доказаното
        task.оборот += 1
    return escalate(task)                          # ESCALATED + запис в журнала
```

Критикът е от **друго семейство модели** от Строителя (намалява общите слепи петна).

## 8. Грешки: класове и автоматично решение

| Клас | Разпознаване | Автоматично действие | Ескалация |
|---|---|---|---|
| `код` | тест/компилация пада | Резолвер получава компактния отчет | след `макс_оборота` |
| `схема` | изходът не валидира | повторно извикване с примера на схемата (макс 2) | смяна на модел, после ескалация |
| `знание` | несъществуващ API/факт | тегли документация -> `knowledge`, повторен опит | ако няма източник |
| `среда` | липсва зависимост, мрежа, токен | опит за поправка на средата (install, retry с backoff) | при липсващ достъп: човек |
| `спецификация` | критерии противоречиви/неизпълними | връща се към Планиста за нова версия | ако Планистът не съгласува: човек |
| `конфликт` | два scope-а се пресичат | сериализира задачите | - |
| `цикъл` | оборот > макс или повтаряща се грешка | **стоп**, пълен контекст на опитите | човек / нова задача |
| `бюджет` | лимит достигнат | пауза | човек |
| `сигурност` | secret в diff, подозрителна команда | **блокира**, карантинира бранча | човек |

**Допълнителни механизми:**
- **Retry с експоненциален backoff** само за преходни грешки (мрежа, rate limit).
- **Circuit breaker:** ако даден модел/инструмент даде N поредни грешки, оркестраторът го изключва за период и ползва резервен.
- **Откриване на повторение:** хеш на (клас, съобщение). При 2 повторения Планистът добавя правило в `rules.md`.
- **Всяка грешка се записва**, дори ако е решена автоматично.

## 9. Сигурност

1. **Недоверен вход.** Имейли, уеб страници и коментари в GitHub могат да съдържат инструкции, насочени към модела (prompt injection). Затова: съдържание от външен източник се подава на агентите само като **данни**, обграден с ясен маркер, и **никога** не може да задейства инструмент с право на запис, пращане на имейл или плащане. Класификаторът извлича факти ("клиентът иска X"), а не изпълнява текст.
2. **Тайни.** Ключовете са в `.env` / мениджър на тайни, не в репото и не в промптове. Агентите не виждат ключовете. Tool Gateway ги прикача на заявката.
3. **Минимални права.** GitHub токен: repo contents + pull requests, без admin. Gmail: само `readonly`. Отделен ключ за всеки модел с месечен лимит при доставчика.
4. **Изолация.** Код се изпълнява в worktree, за предпочитане в контейнер без достъп до домашната папка и без мрежа освен allowlist.
5. **Защита на main.** Branch protection: задължителен CI + одобрение. Агентът няма право да я заобикаля.
6. **Одит.** Таблицата `events` е append-only.
7. **Secret scanning** като гейт на всеки diff.

## 10. Политика на автономност

Идеята: човек се намесва **по риск**, не по навик. Конфигурира се в `policy.yaml`.

| Клас на действие | Пример | По подразбиране |
|---|---|---|
| **Обратими, локални** | код в бранч, тестове, четене на имейл/GitHub | автоматично |
| **Обратими, споделени** | отваряне на PR, коментар в PR | автоматично |
| **Необратими или публични** | merge в main, deploy, публикуване | човек (може да се смени на авто при зелен CI + нисък риск) |
| **Финансови** | реални транзакции, търговия с реални пари | човек, с лимит на сума |
| **Изходящи съобщения** | изпращане на имейл от твое име | човек (чернова се подготвя автоматично) |
| **Промяна на права/ключове** | нови токени | винаги човек |

Нива: `L1` (всичко иска одобрение), `L2` (по подразбиране в таблицата), `L3` (авто-merge при зелени гейтове и нисък риск). Препоръка: започни от `L2`, мини към `L3` за конкретен проект, когато цикълът е доказал надеждността си.

## 11. Входове и радари

```
Gmail (read) ─┐
GitHub issues ─┼─► Класификатор (евтин модел) ─► {задача | информация | шум}
inbox.md ──────┘                                      │
                                            само "задача" влиза
                                            в Планиста като кандидат
```
- Радарите работят с polling (по график), не с постоянни връзки: по-просто и стабилно.
- Всеки елемент се дедуплицира по хеш.
- Класификаторът връща структуриран JSON: `{тип, приоритет, резюме, източник_ref}`.

## 14. Как се тества самият двигател

- **Unit тестове** на state machine (всеки преход, включително невалидни).
- **Fake агенти** (скриптирани отговори), за да се тества цикълът без пари и без модели.
- **Тест за срив:** убиваме процеса в средата на задача и проверяваме възстановяване.
- **Тест за инжекция:** имейл с злонамерена инструкция не трябва да предизвика действие.
- **Golden задачи:** малък набор реални задачи с известен резултат. Пускат се при всяка промяна на промпти или модели, за да се види подобрение или влошаване.

## 15. Фази и критерии за готовност

| Фаза | Съдържание | Готово, когато |
|---|---|---|
| 0 | SQLite, state machine, Agent Runner (`claude -p` + един API модел), Judge с тестове, Журнал на грешките, Budget Guard. Без конектори | 5 поредни задачи минават сами; срив се възстановява |
| 1 | Диалектичен цикъл (Критик с контрапримери), схеми, класове грешки с автоматични решения | Критикът намира поне една реална грешка, която гейтовете пропускат |
| 2 | GitHub конектор: бранч, PR, CI, Policy engine | Пълен PR цикъл без ръчен копи-пейст |
| 3 | Scheduler с паралелизъм, граф на зависимости, Планист и Спецификация | Една цел се разбива и изпълнява в няколко задачи сама |
| 4 | Gmail (четене) + класификатор, `inbox.md`, панел | Идея от имейл става кандидат-задача |
| 5 | Знания (документации), правила от повторни грешки, golden тестове | Измеримо по-малко повторни грешки |

## 16. Ограничения (честно)

- Системата намалява халюцинациите, но не ги нулира. Гаранцията идва от **изпълнима проверка**, затова проекти без добри тестове са най-слабото място. Планистът трябва да създава тестове още в спецификацията.
- За области като търговия резултатът се мери с бектест, paper trading и малки реални суми. Двигателят гарантира метода, не печалбата.
- Качеството зависи от качеството на спецификацията. Неясна цел дава неясен продукт, затова етапът "Спецификация" е най-важният.
- Автономността расте поетапно: първо доказваш надеждността, после намаляваш одобренията.
